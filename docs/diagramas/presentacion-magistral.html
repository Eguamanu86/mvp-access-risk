El problema

La decisión de acceso es binaria

  • EP-Platform (Backend Auth Proxy) valida credenciales y emite la sesión.
  • La decisión de exigir 2FA es binaria y por reglas: dispositivo de confianza o no.
  • Un usuario legítimo que viaja o entra de madrugada paga la misma fricción que un atacante.

Tesis central

Un modelo no es un sistema

  • Un model.json no es un producto: es un artefacto.
  • El modelo no expone, ni degrada, ni audita, ni aprende por sí solo.
  • La inteligencia no está en el algoritmo: está en la ingeniería que lo rodea.
El backend orquesta, la IA opina y el backend decide.

Responsabilidades

Cada capa tiene un rol

web→ gateway→ mock-auth decide→ access-risk-api reglas + fallback→ access-risk-model opina
  • mock-auth: orquesta el login y toma la decisión final.
  • access-risk-api: reglas, fallback, métricas y persistencia.
  • access-risk-model: infiere el score de riesgo. Solo opina.

Concepto

¿Qué es MLOps?

  • MLOps = ML + DevOps + datos.
  • DevOps gobierna el ciclo del código; MLOps añade el ciclo de los datos y del modelo.
  • Tres activos que evolucionan a distinto ritmo: código, datos y modelo.
En MLOps el modelo es un artefacto; el sistema es el producto.

Ciclo de vida

MLOps es un ciclo, no una fase

datos→ entrenamiento→ validación→ registro→ despliegue→ monitoreo→ feedback↺
Si el monitoreo no alimenta a los datos, el ciclo está roto: hay un modelo, pero no hay MLOps.

Datos

Los datos son ciudadanos de primera clase

  • Reproducibles: semilla fija, mismos resultados.
  • Versionados y validados como cualquier otro artefacto.
  • Garbage in, garbage out: ningún algoritmo salva datos malos.

Resiliencia

La IA puede fallar; el login no

  • Timeout duro de 250 ms en cada salto.
  • Circuit breaker: 3 fallos → abierto; 10 s → semiabierto; si responde → cerrado.
  • Fallback en cascada → exigir 2FA. El login nunca se cae.
Degradar con gracia es diseño, no un parche.

Ingeniería

Estándar de implementación

  • Arquitectura hexagonal (4 capas), Node 24, Express 5.
  • Calidad: 16 + 11 + 5 pruebas (modelo, unitarias, integración) + lint.
  • CI/CD: lint → tests → cobertura → SonarQube → despliegue.
  • Cloud Run, Secret Manager, contenedor no root, servicio no público.

Síntesis

Cinco lecciones para llevar

  • Un modelo no es un sistema: el valor está en orquestar y decidir.
  • MLOps es un ciclo: si el monitoreo no vuelve a los datos, está roto.
  • Los datos y las etiquetas son el combustible.
  • La resiliencia es diseño: timeout, circuit breaker y fallback.
  • La puerta de calidad hace confiable la automatización.

Anexo para estudiantes

Dos ritmos y las brechas

Flujo online · ms
Rápido y disponible

Usuario → mock-auth → access-risk-api → modelo. El login nunca se cae.

Flujo offline · horas/días
Reproducible y auditable

Feedback → retrain.py → puerta de calidad → nueva versión.

Pendiente para producción: drift distribuido multi-instancia, registro gestionado, disparador automático de reentrenamiento, rollback/canary y auditoría a gran escala.

Un buen sistema MLOps no es el que no tiene brechas: es el que las conoce y documenta.
